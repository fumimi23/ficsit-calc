# ficsit-calc — kickoff brief

作成日: 2026-08-10（親ディレクトリでの相談セッションから蒸留）

## 目的 / 作りたいもの

Satisfactory で「作りたいアイテムと目標生産数（個/分）」を入力すると、
必要な**機械の種類と台数**・**中間素材と原料の必要量（個/分）**・**合計消費電力（MW）**を
逆算して表示する Web アプリ。

- 計算はレシピグラフを目標から遡って展開する純粋なクライアント側処理。
- サーバー API は不要。レシピデータはスナップショット JSON としてリポジトリに同梱し、
  静的サイトとしてビルド → **GitHub Pages** で公開する。
- リポジトリは **Public**（setup-workflow の既定 Private をこのプロジェクトでは上書きする）。
  Pages は Free プランでは Public リポ限定のため。

## 名前と理由

**ficsit-calc** — 短くタイプしやすく、ゲーム内企業 FICSIT にちなむため Satisfactory 界隈には伝わる。
既存の有名ツール（Satisfactory Calculator / Satisfactory Tools）と名前が丸被りしない。

## スコープ

### やる（v1）
- デフォルトレシピのみの生産チェーン逆算（機械台数・素材量・電力）
- レシピデータ: ゲーム同梱 Docs（`<ゲームフォルダ>/CommunityResources/Docs/en-US.json`、UTF-16）を
  **自前パーサースクリプト**でパースし `data/recipes.json` を生成・コミット
  - スキーマ先行: 計算コアはスキーマ準拠の fixture データで開発し、パーサー完成を待たない
  - 既存 npm の satisfactory-docs-parser は 1.0 以降対応が未確認・テストなしのため参考実装扱い
  - **データ取り扱いポリシー**（Docs は公式がツール開発用に提供しているが明示ライセンスなし。
    コミュニティの確立した慣行に合わせつつ保守的に運用する）:
    - 生の `en-US.json` はコミットしない（`.gitignore`）。コミットは派生スナップショットのみ
    - 抽出は計算に必要な最小限（ID・名前・数量・所要時間・機械・電力）。説明文・フレーバー
      テキストは含めない
    - アイコン等の画像アセットは抽出・同梱しない（v1 の UI はテキストで足りる）
    - リポジトリは Public のため、README に出典（Coffee Stain の CommunityResources 由来）と
      非公式ツールである旨を明記する。**recipes.json を最初にコミットする時点までに必須**
- Web UI 最小版: アイテム選択 + 目標レート入力 → ツリー表示

### やらない（v1 では）
- 代替レシピ（Alternate Recipes）— データモデルは「1 アイテムに複数レシピがありうる」形にしておく
- 代替レシピの自動最適化（線形計画）
- 採掘機・資源純度の計算（原料は「鉱石 n 個/分」のノードで終端）
- オーバークロック / 電力シャード
- 複数目標アイテムの同時計画
- デプロイ自動化（GitHub Pages 公開は v1 後のロードマップ）

## 技術スタック

- **Astro + React アイランド + TypeScript**（静的ビルド）
  - 計算コアはフレームワーク非依存の純 TS モジュールとして分離し、UI を React アイランドで載せる
  - v1（ページ全体が対話的な計算機）では Astro の静的最適化の恩恵は薄く、採用動機は
    「使ってみたい」+ ロードマップ 2 のアイテム別静的リファレンスページ（そこで SSG が
    本領を発揮する）。合わなければ素の Vite + React SPA に退避できる構成を保つ
- **Vitest**（テスト。Astro の `getViteConfig` で設定共有）/
  **Biome**（lint + format、`scripts/check.sh` に `--check` 系で配線）
- Node は `.node-version` でピン留め（nodenv）、依存は `node_modules` に閉じる
- 開発サーバのポートはプロジェクト固定: **5273**（astro.config の `server.port` で固定、README に明記）
- 配信: **GitHub Pages**（プロジェクトページのため astro.config に `base: '/ficsit-calc'` を設定）。
  デプロイ方式（公式 Pages Action / ローカルから `npx gh-pages -d dist`）はロードマップ 1 で決定
- コードのライセンス: **MIT** を想定（公開コミュニティツールの慣行）
- テスト 3 層: `tests/spec`（約束の台帳・issue 番号併記）/ `tests/unit` / `tests/invariants`
  - invariants 候補: 「recipes.json はスキーマ準拠」「全レシピの入出力アイテムはアイテム辞書に存在する」
    「全レシピの機械はビルディング辞書に存在し消費電力が正である」

## 初期 issue（受け入れ条件付き）

### issue 1: 計算コア — 目標アイテム＋レートから生産チェーンを逆算する
fixture レシピデータ（スキーマ準拠・実ゲーム値を模す）に対して:
- 鉄板 30 個/分 を指定したとき、構築機 1.5 台（鉄板）・製錬炉 1.5 台（鉄インゴット 45/分）・
  鉄鉱石 45 個/分・合計電力 12MW（各 4MW × 3.0 台）が算出される
- 複数原料レシピ（例: 強化鉄板）を指定したとき、各原料の枝が再帰的に展開され、
  レシピを持たないアイテム（原料）のノードで終端する
- 同一中間素材が複数の枝から要求されるとき、素材・機械・電力の合計に重複なく合算される
- 存在しないアイテム ID を指定したとき、明示的なエラーになる
- 機械台数は小数のまま保持する（丸め・クロック提案は表示側の関心事）

### issue 2: Docs パーサー — ゲーム同梱 Docs から `data/recipes.json` を生成する
- UTF-16 の `en-US.json` を入力に実行したとき、スキーマ準拠の `recipes.json` が生成される
  （スキーマ検証を通ることをテストで確認）
- 生成物に「モジュラーフレーム」のデフォルトレシピが正しい入出力・機械・所要時間・電力で含まれる
- 代替レシピ（alternate）は既定で除外される
- 手作業で作った建築物専用レシピ等、製造機械に紐づかないレシピは含まれない

### issue 3: Web UI 最小版 — 入力から結果ツリーを表示する
- アイテムを選択し目標レート（個/分）を入力したとき、機械一覧（種類・台数）・原料合計・
  総電力（MW）が表示される
- 中間素材の連鎖が階層（ツリー）で表示される
- `data/recipes.json` をビルド時に同梱し、サーバー API なしの静的配信で動作する

## ロードマップ（v1 以降）

1. GitHub Pages 公開（デプロイ方式の決定、`base` 設定の動作確認、公開 URL を README に記載）
2. アイテム別静的リファレンスページ（`/item/<スラッグ>` を recipes.json からビルド時に生成。
   デフォルトレシピと代表レート（例: 60/分）の標準構成を JS ゼロのページ群として出力。
   Astro の SSG が本領を発揮する機能で、共有可能な URL・検索流入も狙える）
3. 代替レシピの選択式対応（使うレシピをユーザーが指定）
4. 副産物の扱いの改善（余剰表示 → 消費計画）
5. 採掘機・純度、オーバークロック、複数目標の同時計画

## 未決事項

- 機械台数の**表示上の**丸め方（小数のまま / 切り上げ + クロック率提案の併記）→ issue 3 で決める
- 副産物が出るレシピ（原油系など）の v1 での扱い — 「余剰出力として表示のみ」を暫定案とする
- Docs ファイルの入手手順の明文化（Windows 側ゲームフォルダから `data/` へコピーする運用か、
  パス指定で直接読むか）→ issue 2 で決める
- Pages のデプロイ方式（公式 Pages Action / ローカル `gh-pages` push。Public リポなので
  Actions 利用は課金ルール上も問題ない）→ ロードマップ 1 で決める
